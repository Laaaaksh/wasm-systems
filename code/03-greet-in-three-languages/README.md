# 03 — The contract, not the language

The same program - print `Hello, <name>, from <language>!`, where `<name>`
comes from the command line - implemented three times, in Rust, Python, and
Go. All three target the **exact same WIT world**:
[`wit/world.wit`](wit/world.wit), which just includes the standard
`wasi:cli/command@0.2.3` world (no custom interface needed yet - that's
[Stage 4](../../curriculum/04-wit-and-canonical-abi.md)). All three are
built by completely different toolchains and produce a component `wasmtime`
runs identically.

Companion to [`curriculum/03-same-component-other-languages.md`](../../curriculum/03-same-component-other-languages.md).

`wit/deps/` was vendored from the standard WASI package registry with
[`wkg`](https://github.com/bytecodealliance/wasm-pkg-tools) (`wkg wit fetch`,
run once from a scratch directory with a `wit/world.wit` that
`include`s `wasi:cli/imports@0.2.3`) - this is the same mechanism real
component projects use to pin WASI interface versions, not a shortcut
specific to this repo.

Versions this was built and run against: `cargo-component` 0.21.1,
`componentize-py` 0.25.0, `wit-bindgen-go` (part of
`go.bytecodealliance.org/cmd` 0.7.0), `tinygo` 0.41.1, `go` 1.26.5,
`wasmtime` 48.0.1, `wasm-tools` 1.258.0, `wkg` 0.16.1.

## Run it

```bash
make run
```

Expected output:

```
== rust/ (cargo component) ==
Hello, Ferris, from Rust!

== python/ (componentize-py) ==
Hello, Guido, from Python!

== go/ (TinyGo + wit-bindgen-go) ==
Hello, Gopher, from Go!
```

`make validate` runs `wasm-tools validate --features component-model`
against all three outputs.

## Per-language notes

- **`rust/`** - `cargo-component`'s target is declared in `Cargo.toml`
  under `[package.metadata.component.target]`, pointing at `../wit`. This
  is the only one of the three where the world contract is enforced at
  the type level: `Guest`/export bindings are generated Rust traits, so a
  signature mismatch is a compile error.
- **`python/`** - `app.py` implements a class named `Run`, matching the
  exported `wasi:cli/run` interface's generated Protocol
  (`wit_world/exports/__init__.py`, regenerated by `make build-python` -
  not committed, see `.gitignore`). componentize-py resolves this by
  **name**, not by inheritance - nothing statically checks that `Run.run`
  matches the WIT signature until you actually run the component and it
  either works or traps.
- **`go/`** - needs two separate tools: `wit-bindgen-go` generates the Go
  package from the WIT world, then `tinygo build -target=wasip2` compiles
  it to a component. Note what `../wit/world.wit` had to include:
  `wasi:cli/command`, not just a bare custom export - TinyGo's WASI
  component support currently assumes the full command world is present
  (a pure-library "reactor" component without it failed to build as of
  TinyGo 0.41.1, with `wasm-tools component new` refusing for a missing
  `wasi:cli/environment` import). That's a real, current toolchain gap,
  not a mistake in this sample - see
  [`resources/common-pitfalls.md`](../../resources/common-pitfalls.md).

## Things to try

- Change `wit/world.wit`'s package name and rerun `make build-rust` -
  watch `cargo component` fail with a clear error, then make the matching
  change and rebuild. This is the type-checked path.
- Break `python/app.py` by renaming `Run` to something else, rebuild, and
  see what `componentize-py` does instead - contrast that failure mode
  with Rust's.
- Run `make build-go && wasm-tools component wit go/greet_cli_go.wasm` and
  diff it against the Rust build's `wasm-tools component wit` output -
  they should describe the same world, from two completely different
  compilers.
